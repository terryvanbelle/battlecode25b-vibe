# Digest: what bc20, bc21, bc22 and bc26 learned (plus bcenv)

Sources: filtered docs in `~/projects/vibe/reference/readroom-no2025/{bc20,bc21,bc22,bc26,bcenv}/` (LEARNINGS,
TRAINING_ALGORITHM, METHOD, POSTMORTEM, RESEARCH, HANDOFF, DESIGN, BENCHMARK, tools/README, log skims) and source in
`~/projects/vibe/reference/battlecode{20,21,22,26}-vibe/`. Order of projects: bc22 (128 iterations), bc26 (252), bc21
(~63), bc20 (~87, most refined method); later weighs more. Numbers are kept only as evidence for year-agnostic lessons.
Notation: mirror = candidate vs frozen incumbent; peers = own snapshots/archetypes; benchmarks = strong external bots;
ladder = rated scrimmages against an external field.

---

## 0. The ten most important points (details below)

1. Build the instruments (replay dumper, metrics CSV, run differ, bytecode monitor, SPRT gate, tests) before the bot.
2. No test before one logged game shows the mechanism firing; inert changes are the normal failure (1.2, 1.6).
3. Gate with a paired, seeded SPRT on random maps/sides, not a fixed panel (1.1).
4. Self-play gains do not transfer reliably: bc20's six h2h accepts (+311 Elo summed) moved the ladder +12; bc22 never
   beat `camelcase` (0/20, 128 iterations); bc26 was 0/20 vs three strong bots at first contact. Get diverse external
   opponents early (1.5).
5. What converts: removing binding caps, fixing defects, failure-mode preventers, zero-marginal-cost capability. What
   does not: reallocations, more damage, survival bought with inactivity, coordination schemes (2.2, 2.6).
6. Play symmetry from day one: no fixed-order tie-breaks, first-of-scan picks, Team literals, shared seeded RNG (2.5).
7. Bytecode overruns are silent and lose whole rounds: monitor from Iteration 0 (2.8, 3.4).
8. Trace one replay for degeneracy; never sample only losses; correlate to find where, diagnose to prove (1.4).
9. Read the engine for every mechanic relied on; sweep the API for never-called methods (2.1).
10. When stalled: ablate accepted features first (bc26 found +24, +28 and one negative), then structural (1.6).

## 1. Process lessons (training methodology)

### 1.1 The accept gate: what to measure with

- **Resolution matters more than relevance** (bc21 METHOD §1, bc26 "instruments ranked by resolution"). An instrument
  pinned near 0% or 100% (benchmarks at ~3%, old bots at ~88%) resolves only large moves; +/-2 games is its noise
  floor. An even matchup (mirror, ~50% by construction, both sides) makes a 4-game swing real signal.
- **But resolution is not representativeness.** The mirror cannot value a defence against a behaviour the lineage
  never performs. bc26 ablated a trap ring at 57.4% on the mirror (accepted); benchmark early-wipe rate rose 16% ->
  26%; restoring it halved it. "The mirror can prove a feature is not paying for itself. It cannot prove a feature is
  unnecessary."
- **SPRT** (`tools/sprt.py`, 19 lines): batches of 16, random map and side, cap ~240-320 games. Strong changes accept
  in ~100 games; null ones cost the cap. Ladder variant: `--p0 <incumbent rate>`.
- **Paired mirror** (bc20 `paired.sh`/`mirror.sh PAIRED=1`): each cell = random map + side + *fresh engine seed*,
  played as candidate-vs-incumbent and incumbent-vs-incumbent. Under a fixed seed the engine is deterministic, so
  wherever the change never fires the pair is concordant. Only discordant pairs enter the test. An unpaired gate read
  34-46 REJECT when 74/80 pairs were concordant and the rest 4-2 *for* the candidate. At the cap, a sign test on
  discordant pairs (p<0.01, >=12 pairs) decides either way.
- **Seed every game.** With a fixed engine seed, 491 of 2,825 ladder games were exact repeats and a 240-game gate held
  at most 104 distinct games (bc20). Dedupe (teamA, teamB, map, seed) when rating.
- **Deterministic engines: re-running a marginal result yields zero information.** Vary the dose instead (bc26). Only
  non-determinism in these engines was the final tie-break coin flip.
- **Dose-response.** A parameter is a dose only if it changes the evaluated condition. Always measure the zero arm: an
  inverted high dose rejects that dose, not the mechanism (bc26 Iteration 45: 4 cheese 53.7%, 16 cheese 37.0%, zero
  arm 46.3% = interior optimum). A curve peaking in the middle beats any single point as evidence.
- **Head-to-head vs latest accepted snapshot** became bc26's primary accept test after peer archetypes collapsed into
  mirrors. bc20 tightened further after the winner's curse showed up: compare a candidate against *control blocks of
  the incumbent played in the same period*, never against the incumbent's pooled history (acceptance games rated 1791,
  later games 1738). Require first h2h >= one SE, a confirming second h2h, and pooled lower-1SE bound > 0.
- **Swept-map score** (bc26 Iteration 226): count maps won from *both* sides. Against a near-mirror archetype all 27
  maps were side-split: a 50% with zero information. Swept wins cancel spawn advantage.
- **Never read a running batch.** Games ending early (captures, wipes) finish first, so partial tallies are biased
  (bc21: a 0-5 mid-batch read ended 11-5).
- **Pre-register** before touching code: mechanism, decision-point counter, reachability, trigger frequency in other
  games, price vs what it displaces, gate, falsifier, dose ladder with zero arm, and *which instrument decides*. Never
  reinterpret a null afterwards. If the change targets something only external bots do, pre-register a second arm
  against an archetype that has that property.
- **Do not let pre-registered metrics overrule a cheap unrun instrument at thin margins** (bc26 Iteration 112: +1/+1
  on two metrics; `vs_old_bots` disagreed by ten games).

### 1.2 Three cheap checks that cost no gauntlet (bc26)

1. **Arm-to-arm identity**: count (opponent, map, side) keys with identical (result, rounds). `same == n` means the
   change never executed.
2. **Normalise per round**: every counter scales with game length; surviving longer looks like more deaths.
3. **Correlate timestamps before attributing** (5 of 78 deaths within 5 rounds of a throw refuted a theory an
   iteration had been built on).

Plus from bc26 late log: **is the branch reachable** at observed values (resource gates above typical
treasury, vision gates beyond sensing range, counters that stop at the opening burst), and **read the
outer guard** you are nesting the new condition inside. And: **instrument shared pools** (team caps,
treasury, shared array) whenever a change alters who draws on them (cap-bound trap placement failed three
times, each explained differently and wrongly).

### 1.3 Diffing runs by shape (bc22, bc26)

- Diff baseline vs candidate game-by-game on (opponent, map, side), not aggregate win rate.
- Scattered, mixed-direction flips on fragile maps = churn. One-directional, or concentrated on one map/side across
  many opponents = real regression; reproduce and trace it.
- Calibrate churn: bc26's accepted change flipped 44 games 26:18. Heavy churn is the map set's normal response to any
  timing perturbation (9 losses within 1 point of a win; one lost by 0.22%). The discriminators are asymmetry per flip
  and a coherent dose curve, not churn volume.
- Always know what a control run *was* (bc26 compared against a rejected candidate's run because it was newest;
  briefly concluded the gauntlet was non-deterministic). Re-measure controls; never quote stale ones
  (`paired-check.sh` exists because of this).
- Small repro samples miss map-concentrated regressions (bc22: 8 peers clean, full gauntlet found 6 flips on one map),
  especially for build priority, resource thresholds and shared-signal priorities.

### 1.4 Generating hypotheses

- **Trace one replay for a stall** (activity collapsing, resource pinned in a band, a unit oscillating, a building
  never used). bc26's three accepts of one day all came from per-100-round activity profiles.
- **Do not select replays from the loss list**: a low score term in losses is nearly the definition of losing (bc26
  Iteration 222: five iterations chased a "deficit" that was selection bias).
- **In a mirror, inter-team differences are positional**, not policy.
- **Correlation/onset** (bc20/bc21 `correlate.py`, `onset.py`): per metric, within-opponent correlation with result at
  each sampled round; act on the earliest onset only (by mid-game everything correlates; noise floor ~2/sqrt(n)).
  Coverage was the earliest predictor in bc21 but more scouting alone did not win: a marker, not a lever. Rebuilding
  opponents' correlated unit mix lost 0-24 (symptom, not cause).
- **Profile in a game you win** to avoid outcome bias (bc26 Iteration 238: per-rat action rate equal to a finalist;
  the whole gap was 2x army-turns from survival).
- **Generality check**: verify the hypothesis on a second losing game vs a different opponent/map.
- **Check how often the trigger fires in other games** before implementing: "locally outnumbered" was common
  everywhere, so fixes that helped the diagnosed case hurt broadly (bc22, three times).
- **Act-on-it check**: has a prior iteration deliberately established the behaviour you want to change?
- **Read the opponent's actual behaviour** (replays; source only where rules permit) before modelling it. bc22 wasted
  iterations misattributing a doctrine to the wrong benchmark bot.

### 1.5 Opponent pool / instruments

- Keep three instruments with distinct jobs and never conflate them: mirror (does this change beat what it replaces),
  archetype spars / puppets (does it survive a behaviour the mirror never mounts), ladder or external benchmarks (are
  we actually stronger). bc26 RESEARCH: lacking a live ladder, triangulate.
- **Archetypes (sparring partners)**: one per opponent behaviour that beats you (rush, swarm, hunt, expander, siege,
  defector...). **Run an archetype before trusting it**: two of bc21's did not reproduce their target behaviour; an
  expander archetype took 8 centres then lost on votes because it never bid.
- **Archetypes built from your own code collapse into mirrors**: they go stale (inflating scores: 62.5% read as 95.0%)
  or converge (bc26: `pure_cooperator` became byte-equivalent in effect to `bot`). An archetype resolves only to the
  extent it differs *early and structurally*. Keep them regenerated mechanically (`resync_archetypes.py`) from the
  latest *accepted* snapshot, never from `src/bot`.
- **Peer/benchmark split** (bc22/26): peers 30-90% gate acceptance; benchmarks <30% are hypothesis sources played
  every 3rd gauntlet. Retire opponents beaten >=80% twice. Track a fixed every-10th-snapshot roster (`vs_old_bots`)
  for long-run progress since retirement makes the peer rate drift.
- **Rate a ladder by batch Bradley-Terry**, each build its own player (bc20 `elolib.py`). Sequential K=32 Elo with a
  shared rating was play-order dependent (rank 65 -> 4 from easy calibration games). Draw scrimmage opponents from the
  rating band on both sides of you.
- **Puppets** (bc20): replay one side of a recorded external game up to a cutoff round, then hand over to our code.
  Lets a loss be re-run from round N with a candidate on our side, with no external code.
- Rules adopted in bc20/bc26 for honesty: external bots' source never read (bc22 did read vendored sources, which bc26
  explicitly reversed); external bots only as scrimmages (random map/side); no current-year post-mortems.

### 1.6 Loop discipline

- **Loop shape** (bc22/bc26 TRAINING_ALGORITHM): Gauntlet -> pick a losing game -> hypothesis with verification
  thresholds -> instrument -> re-run -> generality check -> solution -> mechanistic verification (won /
  engaged-as-designed with an evidenced reason it could not flip / neither) -> cheap repro sample -> full gauntlet.
  Hyperparameters: WinPct 60, MaxHypothesis 10, MaxSolutions 10, BenchmarkEvery 3, ReproSample 8, NearMiss 5 points, 3
  near-miss refinements.
- bc20's refined funnel (cheapest first): Read (trace) -> Pre-register -> Diagnose (one logged game) -> Gate ->
  Submit. Most candidates die early by design.
- **Never idle; track functional areas.** After 3 consecutive rejects in one area, the next attempt must come from
  another area or the structural track. At least one structural attempt in four.
- **Stall order** (bc20 §7): ablate carried features (pairwise if the ladder dropped after several accepts) -> sweep
  the API -> re-read allowed games for what you were not looking for -> re-read cross-year research -> structural
  attempt -> rewrite.
- **Closed-directions ledger**: each closed avenue with its measurement, kind (refuted / priced below gate / blocked
  on prerequisite / engine-impossible) and a checkable re-open condition. Re-open only on a *changed cause* (bc26: 3
  re-opens, 1 accepted, 2 converted weak rejections into firm ones).
- **Re-test old rejections** only if the mechanism fired and the margin was inside the old resolution (most come out
  worse). A verified fix can be a no-op because its game state never arises (bc22 Sage logic); check engagement.
- **A mechanism that paid when knowledge was poor can stall once knowledge is good** (bc21 save mode).
- **Rewrite vs retrofit** is unresolved: cross-year winners recommend rewrites when strategy changes; bc20's rewrite
  R1 rated ~1630 vs incumbent ~1800 after 10+ stages and was paused. Budget a rewrite as a structural experiment with
  staged measures, not a rescue.

### 1.7 Records and housekeeping

- `TRAINING_LOG.md` append-only (target, trace, pre-registration, counters, gate numbers, decision, lesson; in-flight
  runs named so a fresh session can resume). `LEARNINGS.md` by theme, each lesson naming its measurement ("a lesson
  without a measurement is a belief"). `HANDOFF.md` = current state + gotchas. `PROMPTS.md` = every user prompt
  verbatim. One archived replay per iteration *in the same commit* (lapsed for 14 and ~90 iterations when treated as a
  follow-up step).
- Post-accept routine in one script; regenerate charts every time; nothing stale stays (a chart from an uncommitted
  snapshot depicts something not in the repo). Stage explicit paths, never `git add -A`.
- Label history rows from the code that actually played, not the highest snapshot dir at run time.
- Ops gotchas: `pgrep -c` double-counts games under a `timeout` wrapper; never `pkill -f` a pattern in your own
  command line (write `[p]attern`); kill the batch script, not its `xargs`; verify a wait predicate matches a live
  process before queuing behind it (a re-exec'd script name destroyed a block); two runs never share a class tree;
  prune VM disk (4-8 MB per kept replay) and check `df` before a gate; `git checkout` cannot undo a committed change,
  restore from the snapshot dir; background loops queued inside one tool call die with that shell; `str.replace` that
  matches nothing silently (use `assert old in s`).
- **Test the measuring apparatus.** Every instrument built in one bc21 session was wrong on first use (a CSV column
  misalignment reported cumulative moves as coverage). Integrity checks on live data (coverage in [0,1000]);
  end-to-end smoke tests of every script on synthetic input; run a new tool on a case whose answer you know; "4 of 4,
  perfect" means check the denominator.
- Unit-test the bot's pure logic and **invariants between tuning constants** (e.g. spare cap >= normal cap).
- bcenv: the feedback system is experimental software; producer/consumer contract mismatches (a parser expecting a
  winner label the tool never prints) silently corrupt evaluation. Bind each result to the exact source snapshot;
  never let analysis tools leak into the submission package.
- Infra: small always-on driver VM (tmux, agent) + e2-standard-8 compute VM; bare `java` per game, ~7 in parallel.
  Game cost varies 10x by year (1 vs 2-45 CPU-min); plan gate budgets from measured game time.

## 2. Strategy and tactics lessons that transfer

### 2.1 Engine-behaviour facts that recurred every year (verify again, do not assume)

- Robots act in spawn (id) order from a snapshot taken at round start; a robot built this round first acts next round,
  so one-round orders written at build time are missed by the newborn. Orders must persist a round.
- `senseNearby*` returns bounding-box row-major order, not by distance: pick the best, never the first. Static fields
  are per robot (team state needs the comms channel). Overruns pause mid-instruction with no exception. Indicator
  strings truncate silently at a length limit.
- `canMove`-style checks may not cover every hazard (bc20: water); cooldown may be charged on the tile you leave
  (bc21); building can be blocked by occupancy, not cost (bc22: own structures filled the spawner's build ring, 9,750
  lead unspent).
- The sandbox/instrumenter rejects reflection-flavoured calls (`getClass`, stack traces) and reports only "team has
  errors"; keep the debug class trivial.
- Replay formats have quirks (bc26 packed cheese into a "kings alive" field). Unit stat tables are in replay headers;
  vision vs action-range gaps are exploitable both ways (bc22 Sage hit units that could not see it).

### 2.2 Economy

- **The opening deployment is worth more than any later reallocation** (bc21 +22 points, the first change to carry to
  the ladder: put the whole starting bank into the economy unit at round 1, not scouts first).
- **Find the binding constraint before tuning anything.** Three of bc21's accepts were cap removals; bc26's largest
  jump was a cost-aware reserve; bc20's was spending a reserve nobody spent.
- **Denominate reserves in the unit they buy** (bc26 Iteration 251: reserve = k * current unit cost, since unit cost
  scaled 8x with army size; a fixed 1000 was most generous exactly when the army had collapsed).
- **Two independently set thresholds create dead bands** (cap gate 1200 vs reserve 1000 pinned treasury in a 200-wide
  band for 1900 rounds).
- **Never let a rule stop the economy for something that cannot hurt it** (bc21: one 1-influence scout in sensor range
  halted production; distinguishing real threats was worth 68.8%).
- **A surplus that becomes standing bodies is a surplus wasted**; a reserve nobody spends is bodies nobody has. Spend
  idle bank.
- Use one cheap stable early signal (bc22 `richHome`: resources visible at spawn) to branch many economic decisions,
  rather than re-deriving "rich map" in several places.
- Committed vs discretionary investment: escalating thresholds for each extra discretionary building.
- Multi-producer contention is turn-order dominance (first actor takes the shared pool), not income.
- Single-producer build rate is a hard ceiling; raw mass often beats sophisticated economy (bc22).
- Production can be blocked by bodies standing on spawn tiles; keep the spawner ring clear and give every
  fixed-station role a stall exit (bc20).
- Congestion is a cost: throttle cheap-unit production by local density (2023 teams in bc22 RESEARCH).

### 2.3 Navigation

- Cross-year convergent design: greedy step toward target; bug (wall-following) fallback with Bug2 closest-distance
  exit; stack or memory to escape concave obstacles; unrolled fixed-radius Dijkstra/BFS (radius^2 ~20) for local paths
  when terrain has costs; friendlies as soft obstacles; randomized tie-break as last-resort loop breaker.
- bc26: Bug2 only for **stationary** targets (applied to moving targets it regressed 75% -> 65%); commit to
  wall-following only when blocked by **terrain**, not a transient friendly (-12.5 points otherwise); always try the
  direct move when not tracing (gating it on "closer than ever" left pushed-back units wall-following forever: -15
  points).
- Oscillation guard (last ~6 tiles), sticky targets: a miner recomputing nearest beacon each round ping-ponged;
  committing to one target until reached/depleted was +9.4 points (bc22).
- Filter "nearest tile" targets for reachability and add a stall exit (bc20 builder walked at a cliff for 600 rounds
  with 5,000 idle).
- Measure before optimising nav: bc21 wrote a cost-aware pathfinder, then measured moves equal to the opponent's; the
  real gap was coverage (46% vs 93%). Reverted unrun.

### 2.4 Exploration

- bc26's single most valuable measured behaviour (+28 points by ablation): **reassign the exploration heading when
  stuck** (two cycles without progress). Without it units hit a map edge and oscillate.
- Emergent spreading: per-robot headings from id, repulsion between explorers, momentum term to avoid re-sweeping
  (cross-year research). Coverage predicts wins early but is not itself a lever.
- Knowledge must carry a timestamp: stamp every ownership/sighting claim with its round and let the newer claim win
  regardless of relay (bc21: stale echoes sent 520 units at a centre already owned; refusing echoes blinded a centre
  for 1,200 rounds). Robots born in sealed areas know nothing: re-post map facts.

### 2.5 Symmetry

- Maps are rotationally or reflectively symmetric (3 hypotheses). Infer it by elimination as terrain and structures
  are seen; "Battlecode 101" that bc26 never did, and it concluded the enemy base unreachable partly because it never
  knew where it was.
- Never assume rotation (bc22: wrong on 4 of 10 maps). Look at a guess before rallying around it (bc20 raiders rallied
  1,500 rounds beside the wrong image). Head toward map centre by default.
- bc21 `MapState`: bitmask of hypotheses, `image(l, hyp)`, prune on confirmed enemy base and on sensed empty tile
  where a base would be, reset on contradiction; bounds discovered by `onTheMap` probing when coordinates are offset.
- Play-symmetry audit checklist (bc22/bc26): fixed-order `Direction[]` tie-breaks; hardcoded compass fallbacks;
  `Team.A/B` literals; id use correlated with spawn order; fixed-seed shared RNG (identical values for "corresponding"
  robots on both teams); first-match on scan order; absolute coordinates in slot layout. Test: mirror match vs a
  byte-identical copy, both sides, all maps; any map won by the same package from both sides is a bug. Note fixing an
  asymmetry can still cost win rate (consistent arbitrary preference gave formation cohesion); prefer the
  better-performing side's behaviour.

### 2.6 Combat

- Cross-year micro (bc22 RESEARCH): kite after every attack where cooldowns allow; attack even blind at the last-known
  position; retreat only near death and as a group; target by kills-per-turn (one-shots first); prefer axis-aligned
  moves on ties to keep formation; step onto good terrain after acting; focus fire via one shared target slot (paid
  only once units survived and reinforced the live fight, bc22).
- bc26 counter-evidence: "kite after every attack" was rejected when its premise (move/attack cooldown asymmetry) did
  not hold that year; per-unit target preference was bounded by a narrow vision cone. Check premises against the
  year's rules.
- "Combat gaps" usually trace upstream: production/survival asymmetry, losing a producer first, isolated deaths (bc22:
  kills were 10 vs 9 until a producer-count divergence).
- **Damage does not convert; survival bought with inactivity does not convert** (bc26: five mechanism-verified damage
  increases moved nothing; halving deaths by leashing cost 18 peer games). Units die because they are doing the thing
  that wins games.
- The alternative must be worth less for *that unit*: the immobile unit trapping is free; the mobile unit trapping
  costs its life (bc26).
- Swarms: guard-for-scout trades are the defence and price is the lever (bc21: cheap guards only under a real swarm
  took a top opponent 42% -> 53%). Raids need waves, not trickles (bc20).
- Defensive ("standing") features must be in place early: any scheme that waits for evidence of a rush arrives too
  late (bc26 trap ring confirmed three times).

### 2.7 Communication

- Design the schema before the logic: fixed slots per purpose, one owner/writer each, an explicit clearing condition,
  defined behaviour when a writer dies.
- **Flags gated on "X has not happened recently" stick open in a sustained war** (bc22: three gates became permanent
  off-switches). Verify the condition actually goes false in a long real game.
- Census via accumulator + first-actor-publishes-last-round's-total (live counts, not cumulative).
- Compress: coordinates mod 128 decoded relative to the reader (bc21 `Comms.loc`); sectors instead of tiles;
  log-scaled buckets for wide-range quantities (unbucket rounds up); batch writes from a local cache with dirty flags.
- Messages read on residues or delayed rounds reach only part of the team; re-post durable facts and let newborns scan
  back (bc20). A one-round order flag is missed by newborns.
- Broadcasting can be a liability (bc26: cats hear squeaks). And a broadcast fixing a real defect can lose on its own
  if the freed capacity is not used (bc21 Iteration 36).

### 2.8 Bytecode

- Hot paths use arrays and unrolled reverse loops, never `java.util` collections (counted as your code).
- Exceptions cost ~500, sensing ~100; cache sensing once per turn; cache distances (bc21 cut politician speech
  evaluation from 14.2k of 15k).
- Overrun costs: bc21 home centre over budget lost 213-404 rounds a game and gated a +10% fix at 53%. Read `over=` for
  every robot type before trusting any candidate.
- Overruns appear in the longest, densest games; one-off profiles go stale (bc22 Iteration 127).

### 2.9 Strategy-level regularities

- Basics done robustly beat sophistication; distrust anything needing cross-unit coordination.
- Decide rush vs turtle per game from measured signals (distance, passability, resource density).
- Keep mechanics (nav, comms, economy model) decoupled from strategy; balance patches invalidate thin edges.
- Build a crude exchange-rate model between resources (incl. unit count) for local decisions.
- Beware fitting the fixed map set: bc26's 8 benchmark wins all fell on 3 of 27 maps.

### 3.4 Bot code patterns worth porting

- **Turn loop + bytecode monitor** (bc21/bc20 `Robot.java`, bc22 RobotPlayer ~L230-260, bc26 `reportBytecodeBudget`):
  `round0 = rc.getRoundNum(); try { turn(); } catch (Exception e) { log }`; overrun if round changed, near-miss at 90%
  of `bytecodeLimit`; print `@bc t= used= max= near= over=` periodically and on every overrun.
- **`Debug.java`** (bc21): `@tag k=v` lines at decision points, grep-countable; trivial by design.
- **`C.java` constants + archetype switch** (bc20/bc21): all tuning constants and feature flags in one class;
  `X_ENABLED` booleans make ablation a one-line change; invariant tests over them (`test/bot/ConstantsTest.java`).
- **`MapState.java`** (bc21, 143 lines; bc20 variant 134): bounds discovery, 3-bit symmetry hypothesis mask with
  `image()`, `pruneWithEnemyEC`, `pruneWithEmptyTile`, timestamped `claimEnemy/claimOwn`.
- **`Comms.java`** (bc21): typed flag protocol `[type:4][extra:6][x&127:7][y&127:7]`, reader-relative decode, log
  buckets. Tests in `test/bot/CommsTest.java`.
- **`Nav.java`** (bc21, 100 lines): cost-aware greedy step, 6-tile oscillation guard, per-robot handedness bug
  fallback, `fleeFrom`. bc26 `moveToward` (~L1175-1320): Bug2 with terrain-only commit and the three documented
  pitfalls. bc26 `explore` (~L1460): stuck-heading reassignment.
- **`Dijkstra20.java`** (bc22, 2,388 lines, MIT, vendored from jmerle/battlecode-2022 `camel_case`, generated by its
  `scripts/dijkstra.py`): unrolled within-vision Dijkstra with rubble costs. Port the generator, not the output, for a
  new grid/cost model.
- **Determinism**: per-robot LCG seeded from `rc.getID()`, no `Math.random`, no shared fixed-seed RNG.
- **Unit tests** for pure logic: `test/bot/{Comms,Nav,MapState,Econ,Constants}Test.java` (plain mains, no JUnit) run
  by `tools/unit-tests.sh`.
